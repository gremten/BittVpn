# Матрица состояний («Карта экранов»): критерии, создание и аудит (2026-11-06)

Готовит «Исследование» по поручению автора (ЖР §126), по типу критериев Ф1–Ф25 флоу (`flow_principles_and_audit.md`). Только текст; Figma и журнал не трогал. Пишу «пользователь». Название артефакта «Карта экранов» — рабочее, предложение Исследования, не из источников (ЖР §124). Эталон формата: `screen_map_cards_clean.md`; пилот: `screen_map_pilot_onboarding.md`.

**Как читать пометки.** «Автор» — решение автора, журнал указан. «Источник» — вывод из открытых страниц (`tech_map_validity.md`, разделы 5–6; цитаты там). «Моё» — предложение Исследования, автором не утверждено.

---

## 1. Откуда критерии

- Решения автора: ЖР §129 (один экран — одна колонка, строка «→»), §127 (статус значком, оформление, тема), §33 (флоу без состояний), §120 (отмена заказа при неоплате), §121–§124 (правки флоу, шит отмены, название «Время на оплату вышло», процесс после флоу), §125 (формат карты), §126 (карта принята, правила в скилл).
- Пилот на 9 экранах онбординга (`screen_map_pilot_onboarding.md`): какие критерии нашли пропуски на деле, какие спорили с продуктом.
- Источники: состояния принадлежат экрану (Hurff; NN/g о wireflow), полный набор состояний определяют до рисования (UI/UX Atlas), итог платежа определяет сервер, а не возврат по ссылке (Stripe, ЮKassa), полнота таблицы проверяется перебором (decision table). Прямых источников про «лучшую форму» карты нет.

## 2. Критерии М1–М17

| № | Критерий | Основание |
|---|---|---|
| М1 | **Источник.** Матрица строится из флоу (экраны), сценария (подсценарии), решений автора (журнал), гипотез (раздел «Решения») и макетов проекта. Ничего не придумывать: тексты интерфейса, цены, числа, названия. Нет вводных — карточка «Нет → Дизайн» с описанием ситуации словами или вопрос автору, не догадка | автор §126; моё (формулировка) |
| М2 | **Колонки = экраны.** Порядок колонок — по флоу слева направо (главная линия). Колонка — экран продукта, а не квадрат флоу: если во флоу два квадрата, а в продукте один экран, колонка одна (М3) | автор §125, §129 |
| М3 | **Один экран — одна колонка.** Шит над экраном и состояние с другим наполнением — карточки той же колонки, не отдельная колонка (пример: «Подтверждение отмены» — карточка колонки «Статус заказа»; «Детали страны» и «Купленная страна» — одна колонка «Детали страны», карточки в порядке пути: сначала не куплена, потом куплена; повторы убрать). Проверка: «если бы пользователь видел это на том же экране с другим наполнением или поверх него, это карточка». Колонки по флоу, но слитые — в связке отмечено «один экран»; кандидатов на слияние, где нет решения автора, не сливать, а вынести вопросом | автор §129; моё (проверка) |
| М4 | **Карточка = состояние экрана, три поля на макете:** название состояния; что видит пользователь (1–2 короткие строки простыми словами); → куда ведёт. Строки статуса («Есть», «Решено → Дизайн», «Нет → Дизайн» и т. п.) на карточке **нет**; готовность макета показывает значок (М11). Других полей на карточке нет (основание, узлы макетов, «у кого» — в связке, М16) | автор §125, §127 |
| М5 | **Строка «→ куда ведёт».** Одна короткая строка простыми словами: только куда ведёт действие (экран, «остаётся на экране», выход), без точек с запятой и без «назад — …». Обычное «назад» не пишется (туда, откуда пришёл — по умолчанию). «Назад» — отдельной короткой строкой «Назад: …» и только там, где оно отличается от умолчания (пример: «Назад: Приветствие, анимация запуска не повторяется»; «Назад: шит отмены онбординга») | автор §124, §129; Ф15, Ф25 |
| М6 | **Шапка колонки:** название экрана и одна короткая строка «Откуда» (из каких экранов и мест приходят). «Вход» — не поле карточки, а эта строка | автор §125, §126 |
| М7 | **Общий экран описывается один раз** для всех фич; у него в шапке слово «Общий» и «Откуда» перечисляет входы. Набор состояний пишется на фичу, но состояния лежат у экрана. Если продукт имеет один экран, а во флоу два квадрата, колонка одна (М3), в «Откуда» объединены входы, включая возврат после следующего шага | автор §126 (общий экран); автор §129 |
| М8 | **Стрелки между колонками:** только основной путь вперёд, между соседними колонками, подпись — действие пользователя глаголом из флоу (до 3 строк). Ветки, возвраты, выходы и «назад» — текстом в карточке («→ …»), стрелками не рисуются (пример: «возвращается назад» и «возвращается к стране» не рисовать, в таблице стрелок помечаются «не рисуются») | автор §125, §126 |
| М9 | **Язык.** Слова автора и журнала; «пользователь»; без кодов, ID, номеров гипотез, джобов и узлов Figma, служебных префиксов («Основание:», «Макет:», «Не хватает / у кого:»), строки с кодами, цен, дат, слов из критериев (Ф, Р, М). В кавычках только слова автора. Название состояния — слова автора («Время на оплату вышло»); нет слов — нейтральное описательное, в связке «рабочее» | автор §125, §124 |
| М10 | **«Назад» = туда, откуда пришёл.** Обычное «назад» не пишется; если иначе — отдельной строкой «Назад: …» (М5) (пример: «Выбор целей» → назад в Приветствие, анимация не повторяется). Если «назад» зависит от входа общего экрана, указать в «Откуда» или в карточке | автор §124; моё (правило записи) |
| М11 | **Готовность макета — значок, не текст.** В чистом файле у каждой карточки остаётся статус как **данные для значка**: «Есть» (макет состояния есть в проекте), «Частично», «Нет → Дизайн» (макета нет), «Решено → Дизайн» (решение есть, макет делать или менять), «Правило» (состояния на экране нет, действует правило). На карточке в макете статус словами не выводится: вместо него значок heroicons (filled) и его цвет. Значки: галочка в кружке = «Есть» (зелёный), крестик в кружке = «Нет» (красный); для «Частично», «Решено», «Правило» значки и цвета определяет Дизайн по текущему файлу, в критериях не придумывать. «Есть» только если узел назван в проекте; «по тех. карте, не проверено» — не «Есть». Цветные заливки карточек по готовности не используются | автор §125, §127; моё (определения статусов) |
| М12 | **Оформление карты.** Фрейм (не секция); сверху заголовок, сразу под ним легенда (значок + цвет + значение), ниже через 32 px колонки. Тёмная тема приложения: фон фрейма — токен bg/page, карточки — bg/surface, текст — токенами соответствующего цвета. Шрифты проекта (Martian, стили файла), не Inter | автор §125, §127 |
| М13 | **Статусы сущности (заказ и т. п.) — короткий список «статус → экран.состояние»,** не граф состояний. Список нужен, если сущность имеет статусы, показываемые на экранах; отказ и истёк срок — один исход «Отменён» (ЖР §120); итог оплаты определяет сервер (поток: уведомление или запрос статуса), возврат из платёжки итог не говорит | автор §120, §125 (без графа); источник (Stripe, ЮKassa) |
| М14 | **Базовые состояния — проверка, не артефакт.** Для каждого экрана, где данные приходят с сервера: загрузка, ошибка, пусто; решение «не нужно, потому что…» записывается в связке. Отдельный чек-лист не ведётся | автор §126 (чек-лист не обязателен); источник (UI/UX Atlas, Habr); моё |
| М15 | **Цикл поиска пропусков** (раздел 3): некуда положить состояние; своя цель и действия; кусок экрана; слишком много состояний; действие, которого нет во флоу | автор §126; моё (формулировка, оговорка) |
| М16 | **Связка отдельно:** по каждой карточке — основание (сценарий, ЖР, гипотеза), узел макета, «кому делать», рабочее название. На карте этого нет (как в Ф14 для флоу) | автор §125; моё |
| М17 | **Полнота и чистота (итог):** у каждого экрана продукта из флоу есть ровно одна колонка; каждое решение автора по экрану отражено карточкой; у каждой карточки «→ куда» указывает на существующий экран или выход; нет карточек-сирот; нет технических слов; открытые вопросы вынесены списком, а не догадками в карточках | моё (сводка М1–М16) |

## 3. Цикл поиска пропусков (М15)

Прогон: для каждого экрана и каждой ситуации из сценария и журнала задать вопросы по порядку; находки списком «экран — что нашли — критерий — что делать».

1. **Некуда положить состояние** (ситуация есть, экрана или состояния нет) → нужен экран или правка флоу; сначала вопрос автору.
2. **Своя цель и действия** (состояние отдельное по смыслу для пользователя) → отдельный экран. **Оговорка из пилота и решение автора §129:** критерий спорит с продуктом там, где продукт имеет один экран с вариантами (детали страны и купленная страна). Решение: колонка по экрану продукта, не по квадрату флоу (М3); отдельный экран — только если у состояния другой экран в продукте.
3. **Меняется кусок экрана** (шит, блок, строка) или экран с другим наполнением → карточка той же колонки, не новая колонка (М3).
4. **Слишком много состояний** (больше 5–6 разных по смыслу) → разделить экран на группы состояний (ожидание / после оплаты) или на экраны; делить, только если группы имеют разные цели; в пилоте деление не потребовалось.
5. **Состояние требует действия, которого нет во флоу** → правка флоу (предложить, не рисовать) или отдать смежному флоу (овал).
6. **Второй проход:** после ответов автора и правок повторить прогон; остановка — нет пустых клеток, каждая карточка имеет основание в связке (М16). Второй проход в пилоте не делался.

Что ловит цикл на деле (пилот): состояние между возвратом и подбором, название макета против решения, два возможных «дома» у предупреждения, «Пропустить» на подборе, пустая рекомендация, «Назад» после необратимого шага. Чего цикл сам не ловит: то, что происходит между экранами; это приходит из вопросов разработчику или внешних источников.

## 4. Режим «создать»

**Вход.** Нужны: флоу (свежая версия автора) и сценарий. **Нет флоу или сценария — стоп: «сначала флоу / сценарий».** Нет решений автора по состояниям — не придумывать, «Нет → Дизайн» и вопрос.

**Вопросы автору до работы (В1–В9).** Пронумерованы, автор отвечает по номерам.
1. Какой флоу и какая версия; какие экраны входят в матрицу (сегмент).
2. Какие экраны общие с другими фичами; откуда на них приходят.
3. Какие состояния уже нарисованы (где лежат макеты), какие нет.
4. Какие решения по состояниям уже записаны (журнал, номера).
5. Куда ведёт «назад» на каждом экране (особенно общем).
6. Какие данные приходят с сервера (нужны ли загрузка, ошибка, пусто).
7. Утверждённые названия состояний словами автора; какие названия рабочие.
8. Кому какие карточки передаются («→ Дизайн» и другие).
9. Вывод: чистый текст карточек для Дизайна (образец `screen_map_cards_clean.md`) и отдельная связка.

**Работа.**
1. Список экранов по флоу и продукту, порядок колонок по главной линии (М2); слить квадраты, где в продукте один экран (М3).
2. Для каждого экрана собрать состояния из сценария, журнала, гипотез и макетов (М1); общие экраны — один раз (М7), один экран — одна колонка (М3).
3. Заполнить карточки по трём полям (М4), строки «→» (М5), шапки (М6), «назад» (М10).
4. Статусы как данные для значка (М11); список «статус → экран.состояние» (М13); оформление фрейма, легенда, тема (М12).
5. Стрелки основного пути вперёд (М8); остальное — текстом.
6. Цикл пропусков (раздел 3), базовые состояния (М14).
7. Очистка языка по М9, строка «→» по М5; связка (М16).
8. Проверка М1–М17 (режим «аудит»), «было → стало», повторная проверка.
9. Показать автору целиком; вопросы автору и разработчику списком (до 10).

**Результаты.** Чистый файл карточек и стрелок; связка; находки пропусков; список «статус → экран.состояние»; вопросы; оценка.

## 5. Режим «аудит»

**Вопросы автору до работы (Ав1–Ав6).**
1. Какая версия матрицы свежая (автор главнее репозитория); что автор правил руками и не менять.
2. Какой флоу и сценарий сверять; их версии.
3. Что утверждено решениями (журнал).
4. Где макеты (какие узлы); что проверять, а что принято.
5. Что считать общим экраном.
6. Что не открывали — «не проверено».

**Проверка.** По М1–М17 каждый критерий: «ок» / «частично» / «нет» / «не проверено». Затем цикл пропусков (раздел 3).

**Итоговая оценка (без накрутки).**
- Считаются только критерии «ок». «Частично» — не «ок»; «не проверено» — отдельной строкой, в числитель не входит.
- Критерии без источника или без решения автора в оценку не засчитывать как «ок» по умолчанию.
- Блокирующие: М1 (придумано), М3 (экран размазан по колонкам), М4 (лишние поля, строка статуса на карточке), М5 (непонятная строка «→», «назад — …»), М8 (стрелки назад/ветки), М9 (технические слова, коды, цены) — при нарушении вердикт не выше «доработать».
- Вердикт: «оставить» — все блокирующие «ок», из остальных 11 «нет» не больше двух; «доработать» — иначе; «переделать» — три и больше блокирующих «нет». Границы мои, автором не утверждены.
- Формат вывода: таблица М1–М17 со статусами, находки «было → стало», оценка «N из 17, не проверено K», вердикт, вопросы автору.
