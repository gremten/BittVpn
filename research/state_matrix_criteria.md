# Матрица состояний («Карта экранов»): критерии, создание и аудит (2026-11-06)

Готовит «Исследование» по поручению автора (ЖР §126), по типу критериев Ф1–Ф25 флоу (`flow_principles_and_audit.md`). Только текст; Figma и журнал не трогал. Пишу «пользователь». Название артефакта «Карта экранов» — рабочее, предложение Исследования, не из источников (ЖР §124). Эталон формата: `screen_map_cards_clean.md`; пилот: `screen_map_pilot_onboarding.md`.

**Как читать пометки.** «Автор» — решение автора, журнал указан. «Источник» — вывод из открытых страниц (`tech_map_validity.md`, разделы 5–6; цитаты там). «Моё» — предложение Исследования, автором не утверждено.

---

## 1. Откуда критерии

- Решения автора: ЖР §33 (флоу без состояний), §120 (отмена заказа при неоплате), §121–§124 (правки флоу, шит отмены, название «Время на оплату вышло», процесс после флоу), §125 (формат карты), §126 (карта принята, правила в скилл).
- Пилот на 9 экранах онбординга (`screen_map_pilot_onboarding.md`): какие критерии нашли пропуски на деле, какие спорили с продуктом.
- Источники: состояния принадлежат экрану (Hurff; NN/g о wireflow), полный набор состояний определяют до рисования (UI/UX Atlas), итог платежа определяет сервер, а не возврат по ссылке (Stripe, ЮKassa), полнота таблицы проверяется перебором (decision table). Прямых источников про «лучшую форму» карты нет.

## 2. Критерии М1–М14

| № | Критерий | Основание |
|---|---|---|
| М1 | **Источник.** Матрица строится из флоу (экраны), сценария (подсценарии), решений автора (журнал), гипотез (раздел «Решения») и макетов проекта. Ничего не придумывать: тексты интерфейса, цены, числа, названия. Нет вводных — карточка «Нет → Дизайн» с описанием ситуации словами или вопрос автору, не догадка | автор §126; моё (формулировка) |
| М2 | **Колонки = экраны.** Порядок колонок — по флоу слева направо (главная линия). Шит или другой слой над экраном — вторым рядом под колонкой-хозяином, не отдельной колонкой в основном ряду | автор §125; моё (шит вторым рядом — по поручению §126) |
| М3 | **Карточка = состояние экрана, четыре поля:** название состояния; что видит пользователь (1–2 короткие строки простыми словами); → куда ведёт; статус одной строкой. Других полей на карточке нет (основание, узлы макетов, «у кого» — в связке, М13) | автор §125 |
| М4 | **Шапка колонки:** название экрана и одна короткая строка «Откуда» (из каких экранов и мест приходят). «Вход» — не поле карточки, а эта строка | автор §125, §126 |
| М5 | **Общий экран описывается один раз** для всех фич; у него в шапке слово «Общий» и «Откуда» перечисляет входы. Набор состояний пишется на фичу, но состояния лежат у экрана. Если продукт имеет один экран, а во флоу два квадрата (пример: детали страны и купленная страна — один экран), колонки остаются по флоу, в связке указано «один экран» | автор §126 (общий экран); моё (оговорка из пилота) |
| М6 | **Стрелки между колонками:** только основной путь вперёд, между соседними колонками, подпись — действие пользователя глаголом из флоу (до 3 строк). Ветки, возвраты, выходы и «назад» — текстом в карточке («→ …»), стрелками не рисуются (пример: «возвращается назад» не рисовать) | автор §125, §126 |
| М7 | **Язык.** Слова автора и журнала; «пользователь»; без кодов, ID, номеров гипотез, джобов и узлов Figma, служебных префиксов («Основание:», «Макет:», «Не хватает / у кого:»), строки с кодами, цен, дат, слов из критериев (Ф, Р, М). В кавычках только слова автора. Название состояния — слова автора («Время на оплату вышло»); нет слов — нейтральное описательное, в связке «рабочее» | автор §125, §124 |
| М8 | **«Назад» = туда, откуда пришёл.** Если иначе, писать явно в карточке (пример: «Выбор целей» → назад в Приветствие, анимация не повторяется). Если «назад» зависит от входа общего экрана, указать в «Откуда» или в карточке | автор §124; моё (правило записи) |
| М9 | **Статусы карточки:** «Есть» (макет состояния есть в проекте), «Частично», «Нет → Дизайн» (макета нет), «Решено → Дизайн» (решение есть, макет делать/менять), «Правило» (состояния на экране нет, действует правило, например отказ платёжки → возврат к подбору). Один статус — один цвет; значения цветов хранит карта в Figma, свои не придумывать. «Есть» только если узел назван в проекте; «по тех. карте, не проверено» — не «Есть» | автор §125 (формат); моё (определения статусов) |
| М10 | **Статусы сущности (заказ и т. п.) — короткий список «статус → экран.состояние»,** не граф состояний. Список нужен, если сущность имеет статусы, показываемые на экранах; отказ и истёк срок — один исход «Отменён» (ЖР §120); итог оплаты определяет сервер (поток: уведомление или запрос статуса), возврат из платёжки итог не говорит | автор §120, §125 (без графа); источник (Stripe, ЮKassa) |
| М11 | **Базовые состояния — проверка, не артефакт.** Для каждого экрана, где данные приходят с сервера: загрузка, ошибка, пусто; решение «не нужно, потому что…» записывается в связке. Отдельный чек-лист не ведётся | автор §126 (чек-лист не обязателен); источник (UI/UX Atlas, Habr); моё |
| М12 | **Цикл поиска пропусков** (раздел 3): некуда положить состояние; своя цель и действия; кусок экрана; слишком много состояний; действие, которого нет во флоу | автор §126; моё (формулировка, оговорка) |
| М13 | **Связка отдельно:** по каждой карточке — основание (сценарий, ЖР, гипотеза), узел макета, «кому делать», рабочее название. На карте этого нет (как в Ф14 для флоу) | автор §125; моё |
| М14 | **Полнота и чистота (итог):** у каждого экрана флоу есть колонка; каждое решение автора по экрану отражено карточкой; у каждой карточки «→ куда» указывает на существующий экран или выход; нет карточек-сирот; нет технических слов; открытые вопросы вынесены списком, а не догадками в карточках | моё (сводка М1–М13) |

## 3. Цикл поиска пропусков (М12)

Прогон: для каждого экрана и каждой ситуации из сценария и журнала задать вопросы по порядку; находки списком «экран — что нашли — критерий — что делать».

1. **Некуда положить состояние** (ситуация есть, экрана или состояния нет) → нужен экран или правка флоу; сначала вопрос автору.
2. **Своя цель и действия** (состояние отдельное по смыслу для пользователя) → отдельный экран. **Оговорка из пилота:** критерий спорит с продуктом там, где продукт имеет один экран с вариантами (детали страны и купленная страна — один экран, во флоу два квадрата); решает флоу автора, в связке отметить «один экран».
3. **Меняется кусок экрана** (шит, блок, строка) → состояние того же экрана, не новая колонка.
4. **Слишком много состояний** (больше 5–6 разных по смыслу) → разделить экран на группы состояний (ожидание / после оплаты) или на экраны; делить, только если группы имеют разные цели; в пилоте деление не потребовалось.
5. **Состояние требует действия, которого нет во флоу** → правка флоу (предложить, не рисовать) или отдать смежному флоу (овал).
6. **Второй проход:** после ответов автора и правок повторить прогон; остановка — нет пустых клеток, каждая карточка имеет основание в связке (М14). Второй проход в пилоте не делался.

Что ловит цикл на деле (пилот): состояние между возвратом и подбором, название макета против решения, два возможных «дома» у предупреждения, «Пропустить» на подборе, пустая рекомендация, «Назад» после необратимого шага. Чего цикл сам не ловит: то, что происходит между экранами; это приходит из вопросов разработчику или внешних источников.

## 4. Режим «создать»

**Вход.** Нужны: флоу (свежая версия автора) и сценарий. **Нет флоу или сценария — стоп: «сначала флоу / сценарий».** Нет решений автора по состояниям — не придумывать, «Нет → Дизайн» и вопрос.

**Вопросы автору до работы (В1–В9).** Пронумерованы, автор отвечает по номерам.
1. Какой флоу и какая версия; какие экраны входят в матрицу (сегмент).
2. Какие экраны общие с другими фичами; откуда на них приходят.
3. Какие состояния уже нарисованы (где лежат макеты), какие нет.
4. Какие решения по состояниям уже записаны (журнал, номера).
5. Куда ведёт «назад» на каждом экране (особенно общем).
6. Какие данные приходят с сервера (нужны ли загрузка, ошибка, пусто).
7. Утверждённые названия состояний словами автора; какие названия рабочие.
8. Кому какие карточки передаются («→ Дизайн» и другие).
9. Вывод: чистый текст карточек для Дизайна (образец `screen_map_cards_clean.md`) и отдельная связка.

**Работа.**
1. Список экранов по квадратам флоу, порядок колонок по главной линии (М2); шиты вторым рядом.
2. Для каждого экрана собрать состояния из сценария, журнала, гипотез и макетов (М1); общие экраны — один раз (М5).
3. Заполнить карточки по четырём полям (М3), шапки (М4), «назад» (М8).
4. Статусы (М9); список «статус → экран.состояние» (М10).
5. Стрелки основного пути вперёд (М6); остальное — текстом.
6. Цикл пропусков (раздел 3), базовые состояния (М11).
7. Очистка языка по М7; связка (М13).
8. Проверка М1–М14 (режим «аудит»), «было → стало», повторная проверка.
9. Показать автору целиком; вопросы автору и разработчику списком (до 10).

**Результаты.** Чистый файл карточек и стрелок; связка; находки пропусков; список «статус → экран.состояние»; вопросы; оценка.

## 5. Режим «аудит»

**Вопросы автору до работы (Ав1–Ав6).**
1. Какая версия матрицы свежая (автор главнее репозитория); что автор правил руками и не менять.
2. Какой флоу и сценарий сверять; их версии.
3. Что утверждено решениями (журнал).
4. Где макеты (какие узлы); что проверять, а что принято.
5. Что считать общим экраном.
6. Что не открывали — «не проверено».

**Проверка.** По М1–М14 каждый критерий: «ок» / «частично» / «нет» / «не проверено». Затем цикл пропусков (раздел 3).

**Итоговая оценка (без накрутки).**
- Считаются только критерии «ок». «Частично» — не «ок»; «не проверено» — отдельной строкой, в числитель не входит.
- Критерии без источника или без решения автора в оценку не засчитывать как «ок» по умолчанию.
- Блокирующие: М1 (придумано), М6 (стрелки назад/ветки), М7 (технические слова, коды, цены) — при нарушении вердикт не выше «доработать».
- Вердикт: «оставить» — все блокирующие «ок», остальных «нет» не больше двух; «доработать» — иначе; «переделать» — три и больше блокирующих «нет». Границы мои, автором не утверждены.
- Формат вывода: таблица М1–М14 со статусами, находки «было → стало», оценка «N из 14, не проверено K», вердикт, вопросы автору.
